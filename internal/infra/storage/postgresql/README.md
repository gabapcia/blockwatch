# PostgreSQL Storage

This package provides a PostgreSQL-backed implementation of the storage interfaces required by the Blockwatch system.

## Technologies Used

- **[jackc/pgx/v5](https://github.com/jackc/pgx):** A high-performance PostgreSQL driver and toolkit for Go, used for managing the connection pool and executing queries.
- **[sqlc](https://github.com/sqlc-dev/sqlc):** A tool that generates type-safe Go code from SQL queries, ensuring correctness and preventing SQL injection.
- **[testcontainers-go](https://github.com/testcontainers/testcontainers-go):** Used for integration testing to spin up PostgreSQL containers, ensuring that tests run in a clean and isolated environment.
- **[migrate/migrate](https://github.com/golang-migrate/migrate):** Used within the test suite to run database schema migrations against the test container.

## How It Works

The core of the package is the `Client` interface, which aggregates several storage interfaces from other parts of the application:

- `chainstream.CheckpointStorage`: For persisting chainstream checkpoints.
- `walletregistry.WalletStorage`: For managing wallet registry data.
- `walletwatch.WalletStorage`: For tracking active wallets.
- `walletwatch.IdempotencyGuard`: For preventing duplicate event processing.

The `client` struct is the concrete implementation of this interface. It holds a `pgxpool.Pool` for database connections and embeds the query sets generated by `sqlc`. The `New` function is responsible for creating and initializing a new client, which includes establishing the connection pool and preparing the `sqlc`-generated queriers.

## Unit Test Strategy

The testing strategy for this package relies on integration tests against a real PostgreSQL instance. This is achieved using `testcontainers-go`, which automatically manages the lifecycle of a PostgreSQL Docker container.

A helper function, `setupPostgreSQLContainer`, is responsible for:
1. Starting a PostgreSQL container.
2. Running database migrations using a separate `migrate/migrate` container.
3. Retrieving the connection string.
4. Creating a new `client` instance connected to the test database.
5. Providing a cleanup function to terminate the container and close the client connection after the test completes.

This approach ensures that the tests are reliable and validate the client's behavior against a live, correctly migrated PostgreSQL server without requiring a manually configured instance.
